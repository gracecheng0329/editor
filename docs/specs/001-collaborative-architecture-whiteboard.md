# 多人協作架構白板：產品與技術規格

建立日期：2026-10-10；修訂日期：2026-10-11；版本：v2。用途：產品總規格與後續 SDD／TDD 實作依據。目標：以 2–4 週為時間預算完成可部署、可操作的作品集，支援同一文件 2–5 位同時協作者。

本文件與 GitHub Issue #1 是總規格，不是一次交付全部功能的實作票。完整產品需求保留，交付順序為技術驗證 G0 與五個產品切片 S1–S5；目前皆未實作或驗證。只有前置條件滿足、行為規格定案的獨立切片才可標記 `ready-for-agent`。

主要測試邊界已由使用者確認：兩個獨立瀏覽器透過正式頁面與真實同步服務協作；另透過直接 WebSocket／API 請求驗證伺服器拒絕未授權寫入。

## Problem Statement

工程師需要在討論系統架構時，共同編輯節點與連線、自由手繪補充想法，並把審查意見留在對應位置。若只能交換靜態圖片，修改、討論與版本容易分散；多人同時操作或短暫斷線時，也難以確認最後保存了哪份內容。

本專案同時服務作品集展示：評閱者應能從可操作的產品看到即時同步、多人游標、斷線恢復、權限隔離、討論串與版本還原，而非只能閱讀架構說明。第一版優先完成端到端協作流程。

## Solution

建立瀏覽器中的多人架構白板。使用者以 GitHub 登入、建立文件、邀請編輯者，並透過分享連結讓其他人觀看。持有分享連結的人可在登入後留言；只有擁有者與受邀編輯者能修改畫布。

畫布支援節點、連線、文字、選取、拖曳、縮放、平移與自由手繪。共同編輯者可看到彼此的游標與變更。已開啟的畫布在暫時斷線後仍可編輯，重連後由單一同步引擎處理變更並使所有在線用戶的文件狀態收斂。

留言可錨定於物件或畫布世界座標，支援回覆、@提及與已解決狀態。系統保存自動快照與命名里程碑版本，允許預覽並受控還原。

| 層面 | 技術選擇 | 責任 |
| --- | --- | --- |
| Web app | Next.js + TypeScript + Tailwind CSS | 作品集入口、產品介面、文件與分享頁 |
| 畫布 | tldraw | 節點、連線、文字、無限畫布、手繪、選取與縮放 |
| 即時協作 | @tldraw/sync + Cloudflare Durable Objects | WebSocket 房間、多人游標、同步、重連、衝突處理與畫布持久化 |
| 帳號與資料 | Supabase Auth + Postgres | GitHub 登入、文件中繼資料、邀請權限、留言與版本索引／快照 |
| 留言即時更新 | Supabase Realtime | 推送討論串、回覆、@提及內容與解決狀態的變更 |
| 部署 | Vercel + Cloudflare + Supabase | 分別提供 Web app、協作服務與資料層 |

## User Stories

1. 作為訪客，我希望從首頁理解產品用途及操作方式，以便決定是否試用。
2. 作為使用者，我希望透過 GitHub 登入，以便用穩定身分建立與協作文件。
3. 作為使用者，我希望登入失敗時能看到可重試的提示，以便恢復操作。
4. 作為使用者，我希望登出後不再保有編輯資格，以便結束目前工作階段。
5. 作為文件擁有者，我希望建立並命名文件，以便開始架構討論。
6. 作為文件擁有者，我希望在文件清單開啟既有文件，以便繼續工作。
7. 作為文件擁有者，我希望新文件預設私密，以便在準備完成後再分享。
8. 作為文件擁有者，我希望產生觀看連結，以便讓審查者閱讀文件。
9. 作為訪客，我希望持有效分享連結直接觀看，以便不登入也能了解架構。
10. 作為文件擁有者，我希望邀請已註冊的 GitHub 使用者成為編輯者，以便授權共同修改。
11. 作為受邀編輯者，我希望登入後開啟受邀文件，以便參與協作。
12. 作為文件擁有者，我希望撤銷編輯權限或觀看連結，以便控制後續存取。
13. 作為觀看者，我希望可以平移、縮放與閱讀畫布，以便檢視完整架構。
14. 作為觀看者，我希望產品明確顯示唯讀身分，以便理解可以執行的操作。
15. 作為編輯者，我希望建立、編輯與刪除架構節點，以便描述系統元件。
16. 作為編輯者，我希望用有方向的連線連接節點並加入標籤，以便表達資料流或依賴。
17. 作為編輯者，我希望新增與編輯文字，以便補充設計限制與說明。
18. 作為編輯者，我希望選取、移動與調整物件尺寸，以便整理畫布。
19. 作為編輯者，我希望以不同顏色與粗細手繪，以便快速標示討論重點。
20. 作為編輯者，我希望選取、移動、縮放、刪除或以橡皮擦移除筆畫，以便修正標註。
21. 作為編輯者，我希望看到自己的變更即時呈現，以便保持流暢操作。
22. 作為協作者，我希望看到其他人的游標與身分，以便理解對方正在討論的位置。
23. 作為編輯者，我希望其他人的新增、移動與刪除及時呈現，以便共同完成同一份圖。
24. 作為編輯者，我希望同時修改同一物件後所有人得到一致結果，以便避免不同視窗各自顯示不同版本。
25. 作為編輯者，我希望暫時斷線時仍能修改已開啟的畫布，以便不中斷思考。
26. 作為編輯者，我希望看到連線與保存狀態，以便區分本機待送出變更和已確認保存的內容。
27. 作為編輯者，我希望重連後自動同步離線修改，以便接續協作。
28. 作為協作者，我希望重新開啟文件後仍看到已確認保存的內容，以便放心結束工作階段。
29. 作為編輯者，我希望 undo／redo 不會回退其他人的無關修改，以便安全修正自己的操作。
30. 作為已登入的觀看者或編輯者，我希望在物件上留言，以便讓意見跟隨被討論的物件。
31. 作為已登入的觀看者或編輯者，我希望在畫布任意位置留言，以便討論某個架構區域。
32. 作為協作者，我希望回覆同一討論串，以便保留審查脈絡。
33. 作為協作者，我希望 @提及可存取文件的參與者，以便表達問題的對象。
34. 作為協作者，我希望即時看見新留言與回覆，以便持續討論。
35. 作為協作者，我希望標記討論已解決或重新開啟，以便追蹤審查進度。
36. 作為協作者，我希望被留言錨定的物件刪除後仍能讀取討論，以便保留決策依據。
37. 作為文件擁有者或編輯者，我希望系統建立自動快照，以便找回先前的畫布內容。
38. 作為文件擁有者或編輯者，我希望建立命名里程碑版本，以便記錄提案與審查完成的時點。
39. 作為可閱讀文件的人，我希望唯讀預覽歷史畫布，以便比較先前設計而不影響現場協作。
40. 作為文件擁有者，我希望還原指定版本並保留還原前的快照，以便可以復原還原操作。
41. 作為仍開啟文件的協作者，我希望知道文件已被還原，以便避免將過期編輯重新寫回。
42. 作為作品集評閱者，我希望使用兩個獨立帳號／瀏覽器完成共同編輯、斷線恢復、留言與還原示範，以便驗證產品的工程能力。

## Implementation Decisions

### 已定案的架構與模組責任

1. 採用表列技術組合；沿用現有 Next.js App Router 專案。畫布在瀏覽器掛載，頁面外框、文件中繼資料與登入流程由 Web app 處理。敏感資料不進入公開頁面快取。
2. 產品分成文件存取、畫布協作、留言討論、版本歷史四個業務模組；模組以身分、文件 ID、權限與穩定物件 ID 互動，不要求預先拆成多個套件或 monorepo。
3. 每份文件對應一個協作房間；Cloudflare Worker 驗證連線與路由，Durable Object 承擔房間的 WebSocket 會話、同步與持久化。Next.js／Vercel 不負責長時間 WebSocket 連線。
4. 畫布即時狀態只由 tldraw sync 管理，不加入 Yjs 或第二個畫布寫入來源。使用套件提供的同步與衝突處理，不宣稱本作品自行實作了 CRDT。
5. Postgres 保存文件中繼資料、成員、留言、提及與版本。Supabase Realtime 僅傳遞留言變更通知；重新連線時從 Postgres 補讀狀態，不把即時事件當成唯一資料來源。
6. 畫布形狀採用穩定 ID；連線保存端點關聯。服務、資料庫等架構元件可用自訂 shape 表達，但第一版只承諾可辨識的節點、標籤與有方向連線。
7. 多人游標與在線狀態屬於暫時 presence，不寫入畫布版本。相機位置、當前選取與工具狀態為使用者本機工作階段狀態。
8. 留言獨立保存於 Postgres；自行提供符合權限模型的留言 UI，不同時把同一則留言寫入 tldraw sync。物件錨點保存物件 ID 及局部偏移，座標錨點保存世界座標。

### 資料模型與公開操作契約

9. 文件資料包含文件 ID、擁有者 ID、標題、房間識別、分享是否啟用、分享 token 的雜湊與建立／更新時間。owner 以文件擁有者欄位為準，不重複建立另一個權威 owner 來源。有效畫布世代由 Durable Object 決定；Postgres 若保存世代欄位，只能作為可重建的索引，不參與最終畫布寫入判定。
10. 成員關聯包含文件 ID、穩定使用者 ID 與 editor 權限；文件與使用者組合唯一。第一版邀請對象為已完成 GitHub 登入的使用者，不依賴外部 email 邀請系統。
11. 留言討論串包含文件 ID、作者、物件／座標錨點、最後已知世界座標、open／resolved 狀態、解決者與時間。訊息獨立保存作者、內容及時間；@提及保存訊息 ID 與使用者 ID。
12. 版本包含文件 ID、不可變版本 ID、automatic／milestone／pre-restore 類型、選用名稱、產生者、產生時間、畫布 schema 版本、世代與服務端修訂資訊，以及畫布快照。版本不包含留言、presence、權限或憑證。
13. Web app 對外提供建立／列出／讀取文件、啟用／撤銷分享、授予／撤銷 editor、取得房間存取票證、留言與回覆、解決／重開討論串、列出／建立／預覽／還原版本等操作。具體 URL 與函式名稱在各切片實作時決定。
14. 每項操作由伺服器推導操作者身分。匿名讀取需要有效分享 token；編輯需要 owner／editor；留言需要有效登入及文件閱讀權。版本建立限 owner／editor，還原及權限管理限 owner。
15. 回應區分未登入、拒絕存取、無效或失效連結、過期畫布世代及可重試服務失敗；UI 不得把失敗回應呈現為成功。對無閱讀權者不洩漏文件內容或成員清單。

### 權限與同步

16. 新文件預設私密。分享連結是可撤銷的閱讀能力，不是編輯能力；持連結但未登入者只能閱讀，登入後可留言。
17. Worker 驗證 Supabase 身分及文件權限後，核發或接受短效、限文件／房間／世代的存取票證。viewer 必須由同步伺服器拒絕畫布變更，不能只停用前端工具列。
18. Postgres 以 RLS／受控伺服器操作落實相同權限。分享 token 不等同於公開整張資料表；匿名分享讀取透過驗證 token 的服務取得有限範圍資料。Realtime 的訂閱授權同樣限制於可閱讀文件。
19. 權限撤銷後，新請求立即依最新權限處理；既有畫布連線及留言訂閱最長 60 秒內失去已撤銷的能力。畫布與留言分別設計伺服器可強制執行的到期／撤權機制，不僅依賴客戶端定時重連。撤銷 editor 不代表撤銷分享；持有效分享 token 的原 editor 降為 viewer。離線變更在重連時重新驗權；不再可寫的變更保留於本機供使用者處理。
20. 暫時離線的範圍是「已開啟文件、頁面仍存活」；允許本機操作並顯示待同步。重連後依同步引擎規則處理競爭修改；收斂不代表同一欄位的兩個互斥值都會保留。
21. 同一物件競爭移動採用 tldraw sync 的決定性結果；不彈出選版對話框，也不自動複製成兩個衝突物件。刪除節點時保留相連線條，將被刪節點的端點解除綁定並停留在最後的世界座標；任何結果都不能引用不存在的節點。刪除與修改競爭須收斂到有效文件。
22. 保存狀態區分連線中、離線／待同步、已確認持久化及失敗；只有取得服務端持久化確認才能顯示已保存。若 SDK 沒有足夠訊號，須補最小的服務端確認契約。

### 本次修訂採用的產品預設

下列細節用於使第一版可驗收，沿用前版預設及本次確認的修改策略。產品行為已作為開發目標；SDK 介面及實現方式仍須依技術驗證結果定案，不代表已有可運作實作。

23. 手繪使用整個筆畫作為可移動、縮放與刪除的物件。橡皮擦先採整筆移除，不做像素擦除、筆畫切割或壓感筆刷。
24. undo／redo 限制為目前使用者工作階段內的操作，不能回退他人的無關變更；版本還原另走版本操作，不混入個人 undo 堆疊。
25. 討論串建立者、owner 與 editor 可解決或重開討論；其他已登入觀看者可建立與回覆。@提及限可存取該文件的參與者，顯示提及內容，不寄 email 或推送通知。
26. 物件移動時留言錨點跟隨；物件刪除時保留討論串與最後位置，顯示錨點已不存在。還原後相同物件 ID 再出現時可以重新連結；留言歷史本身不回退。
27. 有新修訂時，健康服務下須在五分鐘內建立涵蓋該修訂或更晚修訂的自動快照，沒有變更不建立；多人同時在線不應重複建立同一修訂。五分鐘是最長正常等待時間，必須涵蓋使用者最後一次修改後停止操作的情況。命名里程碑可立即建立。保存失敗須呈現失敗／重試狀態並在服務恢復後補建，不能顯示成功。
28. 快照從 Durable Object 的權威畫布狀態產生，包含對應修訂與 schema；不接受客戶端任意上傳快照作為可信版本。只記錄已被服務端接受的內容，UI 對尚未同步修改提供提示。
29. 還原由 owner 在線執行，Durable Object 是唯一協調者：驗證目標快照可讀且 schema 相容、短暫停止接受畫布寫入、確認還原前快照已可靠保存，再原子切換畫布內容與有效世代；最後更新 Postgres 索引。切換前所有已確認修改均須包含在還原前快照。客戶端收到新世代後重新載入，舊世代寫入被拒絕。
30. 還原使用穩定操作 ID，Durable Object 持久記錄進度與結果。同一請求重試只產生一次世代切換；還原前快照保存失敗時維持原畫布及世代、恢復正常寫入；世代切換後索引更新失敗時以 Durable Object 為準補寫索引，不能以舊索引回退畫布；回應遺失時可查回既有操作結果。
31. 同時只能有一項還原操作；其他還原請求收到可重試的忙碌結果。還原期間的新畫布寫入不能被當作成功保存。遇到世代衝突時保留仍存活頁面的本機待同步狀態，讓使用者另存為自己擁有的新文件，或明確放棄後重新載入；不能把舊修改靜默重播到還原後畫布。
32. 快照重試與保留策略在 S5 實作前必須固定：重試間隔、最大保留數量／期間、命名版本與還原前快照是否受保護，以及清理後不可再還原的呈現方式。具體數字未在本次討論決定，列為 S5 進場門檻，不能留給實作代理自行猜測或宣稱已具備有限保留保障。

### 權限矩陣與身分轉換

| 能力 | owner | editor | 已登入 viewer（有效分享 token） | 匿名 viewer（有效分享 token） | 無存取權 |
| --- | --- | --- | --- | --- | --- |
| 閱讀畫布、留言與可用歷史版本 | 可 | 可 | 可 | 可 | 不可 |
| 編輯畫布 | 可 | 可 | 不可 | 不可 | 不可 |
| 建立／回覆討論串 | 可 | 可 | 可 | 不可 | 不可 |
| 解決／重開討論串 | 可 | 可 | 僅自己建立的討論串 | 不可 | 不可 |
| 建立命名版本 | 可 | 可 | 不可 | 不可 | 不可 |
| 還原版本 | 可 | 不可 | 不可 | 不可 | 不可 |
| 管理標題、editor 與分享連結 | 可 | 不可 | 不可 | 不可 | 不可 |

- editor 撤權後，只有同時持有效分享 token 才能降為 viewer；僅知道文件 ID 或分享仍啟用並不構成閱讀權。未持有效 token 者失去存取權。
- 分享撤銷只終止由該 token 派生的能力；owner 與仍有效的 editor 保留原權限。已下載內容不屬於可撤回範圍。
- 分享者取得留言閱讀資格時，服務端須先驗證分享 token。匿名觀看者可經受控讀取介面讀取留言；登入本身不會自動授予文件閱讀權。
- 留言持久化請求逐次驗權。Realtime 若採 Broadcast，分享存取必須映射為伺服器可驗證、短效且限文件的訂閱資格；廣播只包含變更識別與修訂，客戶端經受控讀取補抓內容。若採 Postgres Changes，須證明該身分與 RLS 能表達分享權，不能開放全表閱讀。
- 訂閱到期後，伺服器必須停止傳送新的事件；不能假設資料表 RLS 改動就立即撤銷既有 Broadcast 訂閱。採用哪一種資格與撤權實現方式，在 S4 進場前以整合測試定案。

### 可驗收情境

| ID | Given／When | Then |
| --- | --- | --- |
| AC-01 | 使用者完成 GitHub 登入並建立文件 | 成為 owner，文件預設私密，重新開啟後標題與內容仍存在 |
| AC-02 | owner 開啟分享，匿名訪客持連結進入 | 可閱讀、平移與縮放；不能修改畫布或送出留言；登入後可留言 |
| AC-03 | 兩個不同 GitHub 身分皆有 editor 權限，A 新增節點與連線 | B 看見相同物件與關聯；受控測試環境中，遠端變更於兩秒內可見 |
| AC-04 | A、B 同時移動同一節點，再停止操作，連線健康 | 從最後一次操作起五秒內兩端的文件物件及綁定一致；不多出衝突副本、不損壞節點或連線 |
| AC-05 | A 暫時離線，A 新增節點與筆畫，B 在線新增不同節點，A 重連 | 同世代且仍可寫時，十秒內恢復連線，連線恢復後五秒內收斂且保留互不衝突的新增；離線期間不顯示已雲端保存 |
| AC-06 | viewer 或跨文件使用者繞過 UI 直接發送修改 | WebSocket／API／資料層拒絕未授權操作；owner 重新載入後確認無變更 |
| AC-07 | A 在節點留言，B 回覆並標記已解決 | 兩端看見相同討論與狀態；節點移動時錨點跟隨；刪除後討論仍可讀 |
| AC-08 | A 在世界座標留言，B 以不同縮放比例查看 | 留言指向相同畫布位置，提及身分與內容正確 |
| AC-09 | owner 建立命名版本、繼續修改後預覽版本 | 預覽呈現建立時的畫布；目前協作房間內容不被預覽操作改動 |
| AC-10 | owner 還原舊版本，B 在線，C 持有舊世代離線修改 | B 收到還原狀態並載入新世代；C 重連時舊寫入被拒絕，看到可處理待同步內容的提示；還原前版本可讀 |
| AC-11 | owner 撤銷 editor 或分享權，原連線仍開啟 | 新請求依最新權限處理；既有連線最長 60 秒內失去已撤銷能力。原 editor 持有效分享 token 時降為 viewer，否則拒絕存取；撤銷分享不影響 owner／editor |
| AC-12 | 畫布已確認保存，協作服務重啟後重新開啟 | 已確認的節點、連線、文字與筆畫恢復；版本與留言仍可讀 |
| AC-13 | Realtime 中斷後有其他人留言，稍後恢復 | 從 Postgres 補讀後呈現正確討論串，不遺漏或重複訊息 |
| AC-14 | A 修改物件一、B 修改物件二，A 執行 undo | A 的操作可撤回；B 的無關修改仍存在 |
| AC-15 | 依下述基準，以五個獨立會話對 500 個畫布物件操作五分鐘 | 所有會話可繼續操作，健康連線下遠端變更兩秒內可見，停止操作後五秒內文件收斂；無未處理錯誤，保存狀態正確；S4 起加驗留言一致 |
| AC-16 | 有新修訂後使用者停止操作，或已保存修訂後沒有新修改 | 健康服務下五分鐘內建立涵蓋新修訂的快照；無變更不新增。保存失敗不宣告成功，服務恢復後依 S5 定案政策補建 |
| AC-17 | 節點有連線及物件留言，另一人刪除節點 | 線條端點解除綁定並保留最後位置，沒有指向已刪節點的綁定；討論保留且顯示錨點不存在；健康連線下五秒內各端一致 |
| AC-18 | 同一還原操作重試、還原前快照保存失敗、切換後索引失敗，或成功回應遺失 | 重試不重複切換世代；切換前失敗維持原內容；切換後依權威結果補索引；查詢操作結果可恢復正確狀態 |
| AC-19 | 已登入／匿名分享者訂閱留言，owner 撤銷分享；持有舊資格的客戶端繼續接收 | 新留言讀取立即拒絕；最長 60 秒內停止該分享資格的即時事件；不能靠竄改文件 ID 或忽略客戶端重連來維持訂閱 |

驗收時間與負載是待 G0 校準的開發基準，不是量測結果或公開 SLA。基準採桌面 Chromium、同一測試區域的五個獨立會話及 500 個物件（含 300 節點、100 連線、100 筆畫）；每個會話每秒提交一次移動或新增，持續五分鐘。S4 起另由每個會話每十秒送出一則留言。記錄瀏覽器與套件版本、執行機器資源、服務區域及實測網路條件；不同條件的結果不能直接互比。超過門檻應記錄失敗與原因；若需調整基準，先更新規格，不能以測試重試掩蓋失敗。

## Testing Decisions

1. 保留已確認的產品驗收邊界：Playwright 獨立 browser contexts，以不同穩定使用者身分操作正式頁面，連接真實測試版 Worker／Durable Object 與 Supabase。E2E 集中在建立／分享／共同編輯、離線重連、留言與版本還原等核心旅程，不把全部錯誤組合都塞進瀏覽器測試。
2. 測試只斷言可觀察行為：另一位使用者看到的物件、位置與討論、拒絕寫入、重新載入後的資料，以及保存與錯誤狀態。不斷言 React 元件樹、SDK 私有 store 欄位、訊息內部格式或套件呼叫次數。
3. 權限測試補充一個必要邊界：直接對公開 API、同步協定與資料層送出 viewer／未授權請求，驗證 UI 以外的服務端授權。不能用隱藏按鈕或前端唯讀旗標當成授權測試。
4. 測試範圍涵蓋文件存取、畫布協作、留言討論與版本歷史，對應 AC-01 至 AC-19。權限矩陣、重試去重、索引失敗及保留策略主要透過服務公開介面的整合測試驗證；純規則有足夠複雜度時才補單元測試。這些整合測試是快速 TDD 迴圈，E2E 是各切片的產品驗收。
5. 暫時斷線由測試控制網路或同步連線，不 mock 自動合併結果。以重新連線、明確完成狀態與有期限的條件輪詢判斷收斂，不用固定 sleep 假設成功。
6. 在測試環境預先建立獨立身分與文件資料；多數 E2E 使用合法測試 session，避免每次跑 GitHub OAuth。另保留正式 GitHub 登入 smoke test；不能在 production 引入測試用登入後門。
7. 確認持久化須透過重開頁面及測試版協作服務重啟驗證；不能只比較兩個仍存活分頁的畫面。自動快照以可控制的排程觸發驗證，無須真等五分鐘。
8. 必測版本還原與舊世代離線修改、還原的四類失敗、權限撤銷後重連、寫入失敗、Realtime 漏接及留言錨點刪除。故障注入限測試環境的服務邊界，仍使用真實同步與持久化路徑，不模擬一個預期合併答案。清理各測試的獨立身分／文件／房間，防止測試互相污染。
9. 本 repository 目前為 Next.js 起始模板，沒有既有產品測試、Vitest 或 Playwright 設定可沿用。實作第一個切片時加入最小必要測試基礎；規格本身不預先新增應用程式或測試框架。
10. SDD／TDD 循環：選取一個驗收行為、寫會失敗的測試、完成最小實作、測試通過後整理程式，並更新規格。測試套件、型別檢查、lint 與 production build 均列入各切片完成條件。
11. 同步兩秒可見與五秒收斂是受控測試目標，不當成所有地區網路的 SLA。一般功能測試用較小固定資料集快速執行；500 物件／五會話的 AC-15 在該切片交付及部署前執行，保留觀察條件與結果。
